### F1 [P1] ExportRetry 内の一過性障害で再試行が永久停止する（以前から）

場所: `game_room.rs:handle_export_retry_alarm`。
[根拠: 2349 行以降](https://github.com/SH11235/rshogi/blob/a19c7fe53a1d9ee8e50b6bc9b401ff552994b883/crates/rshogi-csa-server-workers/src/game_room.rs#L2349)

- 再現条件 A: 初回 R2 失敗で pending を保存した後、retry の pending get が失敗する。
  `.await.ok().flatten()` が障害を不在に変換し、タグ・alarm を削除して Ok。本文は残るが起床契機が無い。
- 再現条件 B: 初回 R2 失敗に続いて retry の R2 も失敗し、pending 更新または次の set_alarm が失敗する。
  両方とも失敗を吸収するため、消費済み alarm の代わりが無いまま Ok になる。
- crash でも、元コードは R2 失敗と以降の失敗を吸収して Ok に到達し得る。
  KEY_FINISHED のガードにより通常の確定経路は再開しない。

修正: get 障害を伝播し、R2 より前に次の alarm を予約する。進捗保存の失敗は本文と予約を残す。
alarm 入口は予約が確認できる場合だけエラーを吸収する。
上限の保存後に古い alarm が再配信された場合は、R2 を実行せず停止する入口ガードも追加。
上限後の pending 本文は削除しない。上限後に原本が失われる穴自体は無かった。

### F4 [P2] set_alarm 失敗で finalization の猶予を消費する（PR #1078 の新しい機構に残った穴）

場所: `game_room.rs:finalize_game`。
[根拠: 2101 行以降](https://github.com/SH11235/rshogi/blob/a19c7fe53a1d9ee8e50b6bc9b401ff552994b883/crates/rshogi-csa-server-workers/src/game_room.rs#L2101)

## await 境界の追跡

| 境界 | エラー / isolate 破棄で残るもの | 再開契機と結果 |
|---|---|---|
| 終局手 append_move | SQL 保存前なら入力は未記録。保存後なら終局手まで残る | 既存 turn/agree alarm や受信イベントで replay。記録前に失われた入力の裁定は再現できず、通知前なので別裁定になり得る |
| record_verdict の get / put | put 成功前は裁定未記録、成功後は結果・時刻・broadcasts・attempt=0 | 既存 alarm / 次イベント。保存後は同じ裁定を優先し、replay や切断裁定で上書きしない |
| ensure_finalization_alarm の get / set、attempt put | 修正後は予約成功前に attempt を進めない。予約後に put が失敗しても旧 attempt と alarm が残る | alarm / runtime 再試行。予約済みなら後続エラーを短間隔の自動再試行へ渡さない |
| config get / export の load_moves | 保存済み裁定と alarm、moves が残る | 次回の同裁定で再試行。load_moves は上限で諦めても keep_moves |
| 4 つの R2 PUT | 各 object は固定 key と固定終局時刻から生成した本文。部分成功があり得る | 確定前は同じ本文で再 PUT。確定後は保存済み pending。R2 の応答喪失でも overwrite は冪等 |
| floodgate history append | entry_key と本文は保存した終局時刻・裁定から生成 | 同一 key の R2 PUT。追記という API 名でも JSONL ファイルへの追記ではない。上限後の履歴欠損は設計上の許容 |
| KEY_EXPORT_PENDING put | 失敗時は KEY_FINISHED が未保存、moves も残る | finalization alarm で再構築。成功後 crash でも本文は永続化済み |
| KEY_FINISHED put | 成功前は再確定可能。成功後は裁定確定済み | export pending 有りなら残存 alarm と orphaned_export。無ければ棋譜は R2 または keep_moves |
| finalizing delete / delete_alarm / grace state delete / retry tag・alarm 設定 | finalizing の残骸は finished ガードで無害。pending 有りでは既存 alarm を保持 | 種別が未保存・残存のどちらでも orphaned_export。live-index 削除前 crash は cron 回収 |
| live-index R2 delete / backoff | R2 live entry が残る場合がある | cron が primary meta を照合。meta 無しでも既存の72時間 hard TTL が回収。これは恒久停止の指摘にしない |
| clear_moves | 通常経路は R2 完了か pending 本文がある場合のみ削除 | 失敗は原本残置。途中で clock credits だけ残っても finished ガードで replay しない |
| ExportRetry の get / 先行 set_alarm | 読込失敗を不在に変換しない。予約失敗時は本文を維持 | Err による runtime 再試行。予約後は以降の障害でも後続 alarm を維持 |
| ExportRetry の R2 / pending 更新 | 更新失敗なら古い全文と対象 key が残る | 同じ key の再 PUT。上限を保存できた後は stale alarm でも追加 PUT しない |
| 完了印 put / pending delete / kind delete / alarm delete | 完了印前は本文と alarm。完了印後は R2 と完了印 | pending が残れば再 PUT 可能。pending 消去後は完了済みなので残存 alarm は掃除だけ |

`deliver_terminal` と snapshot の send / attachment 更新 / close は同期 API であり、Rust の await 境界ではない。
ただし送信前の in_flight 保存 → send → sent 保存の各境界も別途確認した。
最初の保存失敗では未送信、send 失敗または sent 保存失敗では in_flight / abort が再送を防ぐ。
保存と send の間に破棄された接続も再開時には 1011 へ進む。
WebSocket send 成功はアプリケーション受信 ACK ではなく、このレビューはその API 成否に基づく保証である。

## snapshot と finalization の競合

通常の進行中 snapshot は storage 操作と同期 send で構成される。
Cloudflare の input gate が storage 待機中の他イベントを止めるため、各 await に無条件で終局イベントを差し込めるとは扱わない。
R2 待機は他イベントを許すため、実際に競合可能な窓として次を検査・テスト化した。

1. finalization の R2 PUT 待機中に新しい観戦者が snapshot を完了する。
   初回 dispatch 済みで再入 guard も立っているため、元コードでは未配信のまま最終 close(1011)。
   これは元の穴1の正常 close 取り違えではない。今回は外部 I/O 後にもう一度 dispatch し、正常配信を回復する。
2. KEY_FINISHED 保存後の live-index delete 待機中に、既存観戦者が再 snapshot を要求する（F6-B）。
3. finished snapshot が pending / R2 から原本をロードしている間の close。
   API のエラー / 中断は 1011 として扱い、未完了を terminal_sent にしない。

根拠: [Cloudflare input gate](https://developers.cloudflare.com/durable-objects/reference/glossary/)、
[alarm の実行中 getAlarm と再試行仕様](https://developers.cloudflare.com/durable-objects/api/alarms/)。

### R1 [P2] ExportRetry の観測が undefined を完了と判定する（#1078 のテスト）

### R3 [P2] 確定済み snapshot の原本読込失敗を正常な空棋譜にする（以前から）

### R4 [P2] 初期 snapshot 本体に入る前の失敗で接続を放置する（以前から）

場所: `game_room.rs:fetch` / `send_finished_spectator_snapshot_if_needed`。
再現条件: 確定済み対局の観戦 upgrade で、accept 後の finished/config 読込が失敗する。
元コードは Err をログにして status 101 を返すが、接続を閉じない。
本体の `send_spectator_snapshot` にまだ到達していないため、その中の中断処理も通らない。
確定後には alarm が無い場合があり、無通信の観戦者は snapshot も結果も受け取れず待ち続ける。
修正: fetch 側のエラー出口でも共通の snapshot 中断処理を呼び、abort 印と 1011 を残す。
config 読込障害（BEGIN 前）と pending 読込障害（BEGIN 後）の回帰シナリオも追加。
これはエラーが返るケースの修正であり、任意の時点での isolate kill に対する close 到達保証ではない。

根拠: [44ec7fd9 の CI](https://github.com/SH11235/rshogi/actions/runs/34510489336) は smoke 82 passed / 4 failed。
この結果は CI 上の実行であり、ローカル sandbox で Miniflare を実行したものではない。
